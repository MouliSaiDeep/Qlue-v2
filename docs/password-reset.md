# Password recovery

The login screen's **Forgot Password?** action and the profile screen's
**Reset Password** row open the same recovery dialog. Login prefills the typed
address. Profile displays the captured Firebase account's address read-only and
checks that the signed-in UID still matches when sending. Google-only profile
accounts are directed to their Google Account rather than adding a password.

Recovery uses `FirebaseAuth.sendPasswordResetEmail` and Firebase's default
HTTPS hosted reset page. The user opens the email, chooses a new password and
signs in again. This is an email-link password reset; signup email verification
continues to use the existing six-digit OTP flow. No new AWS endpoint, SES
identity, IAM permission or backend deployment is needed for password recovery.

Firebase owns reset-token generation, expiry, single-use confirmation and
password storage. The app never reads or stores a reset token or new password
from the hosted page. It supplies no caller-controlled redirect URL. Sending a
request does not sign in/out, verify an account or change a password. Completing
a valid reset revokes existing Firebase sessions, as verified with the real
provider and the backend's existing revoked-token verification behavior.

The app validates and normalizes addresses, prevents simultaneous sends and
applies a 60-second cooldown across dialog closes and changes of email address
within the running AuthProvider. This is a UX safeguard; Firebase's server-side
abuse limits remain the security boundary. The cooldown is not persisted and
does not replace server protections. SDK requests have a 20-second UI deadline;
a timeout warns that delivery could not be confirmed and asks the user to check
their inbox before retrying. Closing a pending dialog is safe.

The confirmation is neutral for existing/unknown/disabled accounts. Provider
errors never expose raw SDK messages. No email-method discovery API is used.
The existing project's server-side email-enumeration protection was checked and
is enabled. The API returns the same successful status and response shape for
existing and unknown addresses; it echoes the submitted address in both cases.

The live Firebase project `qlue-backend-2c0c7` now enforces the same password
requirements as app signup: at least eight characters, uppercase, lowercase,
number and special character. The existing profile password-change form also
checks these requirements. The narrow provider configuration update changed
only `passwordPolicyConfig`; email notifications, sign-in methods and privacy
settings were preserved. `forceUpgradeOnSignin` remains false, so existing users
are not required to change passwords before logging in.

  sign-out/account switching, Google-only accounts, weak-password validation,
  cancellation, timeout and disposal during an outstanding request.
- Real Firebase checks used one uniquely named synthetic account per run. The
  provider accepted a reset-email request to AWS's mailbox simulator, gave a
  neutral response for an unknown address, served its HTTPS hosted reset page,
  rejected an invalid code and weak password, accepted a valid reset, rejected
  the old password, accepted the new password for the same UID, rejected replay
  and revoked the old session. All synthetic accounts were removed.
- The reset action used for confirmation testing was generated by Firebase
  Admin for the synthetic account; it was not retrieved from an email inbox.
  Actual inbox receipt and a physical-device email/browser round trip remain
  untested.

The reproducible live provider harness is `audit/password-reset-live-smoke.cjs`;
it keeps passwords, tokens, credentials and reset links in memory and logs only
sanitized check results. `audit/check-password-reset-config.cjs` reads the
relevant provider configuration. `audit/secure-password-reset-policy.cjs`
records the exact policy before application and refuses to overwrite an already
configured policy without inspection.
